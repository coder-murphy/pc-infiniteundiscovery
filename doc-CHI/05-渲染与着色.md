# 05 渲染与着色

本章是这份整理里证据最强的一部分：着色器不只是"看到字符串"，而是**全部解码、解析、反汇编，并通过了指令与常量表的一致性检查**。

## 1. 渲染框架（来自 RTTI）

```
RenderPassManager / RenderPassManagerList     多通道渲染
RenderableObject / RenderablePrimitive / Primitive   可渲染对象与图元
PrimitiveBufferXe                             Xenos 专用图元缓冲
ShadowManager / FrustumObject                 阴影与视锥
TextureHandler / ITextureHandler              纹理句柄
TextureModifier / TextureModifierManager      运行时纹理修饰
```

后处理类：

```
BackBufferEffect / CameraFilter
BrightnessContrastFilter / MonotoneFilter
FramePersistanceEffect（原文拼错）/ CrossFader
```

这些类名给出的是**框架形状**：通道管理、对象/图元抽象、阴影、纹理修饰、后缓冲滤镜链。真正的渲染内容要看着色器。

## 2. 着色器在哪、有多少

全部在 `ud1.bin`，且**两张光盘逐字节相同**：

| 位置 | 内容 | 程序数 |
| --- | --- | ---: |
| `ud1.bin +0x7800` | 1 个 `AHSX` 缓存，26 条记录 | 21 |
| `ud1.bin +0xC000` | **固定库**：索引 + 60 个 blob | 60 |
| `+0x1F947000` 起 | **9 个 `AHSX` 缓存**，首尾相接 | 63 330 条记录 |

九个缓存原本被容器扫描当成"630 MB 的 ASF/WMV 视频流"。实际拆开后是：六段 WMV 影片（45、158、217、13、28、249 秒）、一个 100 KB 的 `AIF ` 纹理、九个缓存，然后才是下一个归档。`ud2.bin` 没有缓存。

合计 **10 个缓存、96 853 条记录**（63 351 条压缩着色器记录 + 33 502 条别名），去重后 **20 517 个不同程序**。固定库 60 个，所以整张盘共有 **20 577** 个程序。

## 3. 固定库：60 个

* 54 个像素着色器、6 个顶点着色器。
* 由 **9 个不同编译器版本**构建，从 `2.0.4025.0` 到 `2.0.6534.0`。
* 没有一个由 `2.0.6534.1` 构建——那是构建所有缓存程序的编译器。

内容：视频 YUV 转换、景深家族、天空、全屏滤镜，以及水面模拟（见 §7）。编译器版本分布是项目考古：固定库是**增量添加**的，从未整体重建。

## 4. `AHSX` 缓存结构

`AHSX` 就是执行文件里 `e:\AHSLCacheUD4\AHSLv2DiskCache` 路径所指的东西。这一点由三段反汇编确认：

* 构造函数 `0x82219818` 写入版本 `0x002E` / `0x0003` 与两条开发机路径；
* 建空缓存 `0x82217900` 用 `lis/ori` 构造 `AHSX`；
* 加载器 `0x822190A8` 校验版本并逐条读取记录。

头部：

| 偏移 | 大小 | 字段 |
| --- | --- | --- |
| `0x0000` | 4 | `AHSX` |
| `0x0004` | 4 | mask（创建时清零，各缓存不同，未解释） |
| `0x0008` | 2 | `0x002E` 版本 |
| `0x000A` | 2 | `0x0003` 版本 |
| `0x000C` | 2 | 记录数 |
| `0x0010` | `0x2000` | 8 KB 字典 |
| `0x2010` | | 记录 |

记录：

| 偏移 | 大小 | 字段 |
| --- | --- | --- |
| `+0x00` | 2 | 哈希（不是 key 的 CRC-16，未解释） |
| `+0x02` | 2 | 落盘大小（含头） |
| `+0x04` | 2 | 解码后大小 |
| `+0x06` | 2 | 编码部分起点 |
| `+0x08` | 2 | 字典 CRC-16 |
| `+0x0A` | 1 | flags；`0x20` = 重定位指针，标记别名 |
| `+0x0C` | | key（最长 300 字节） |

* key 的第三字节是**它自己的长度 mod 256**；`+0x06 − 0x0C == align4(length)` 在全部 96 853 条记录成立。
* 两种记录：**着色器**（落盘 < 解码后）用 tri-Ace 的**半字 LZ77**（即 SLZ method 3）压缩，字典预置为历史；**别名**（大小相等，flag `0x20`）8 字节，指向更早记录的 key——同一个程序的不同排列只存一次。
* 字典 8 KB，十个缓存完全相同，其 CRC-16/X.25 为 `0xC2E6`（全部 96 853 条记录都记录这个值）。字典看起来像十个着色器，其实是被裁掉常量表片段的**压缩字典**——一个 752 字节的顶点着色器能压到 74 字节。8 KB 的尺寸不是巧合：method 3 的距离是 12 位、按半字计数，最远回看 4 095 × 2 = 8 190 字节，正好略小于字典大小。

## 5. 编译产物与反汇编

* 记录解码后是 0x18 字节头 + 微软 XDK 的编译着色器 blob（含 D3D9 `CTAB` 常量表）。
* 执行文件里带着 **Microsoft 整个 Xenon 微码编译器**（HLSL 前端、优化器、寄存器分配器、R500 汇编器，连诊断字符串都在）。因此反汇编器可以使用**微软自己的 opcode 名**：编译器里的 opcode 表有 **103 行**。
* 关键校验：**指令实际读取的寄存器，必须与它自己的常量表声明一致**。在全部 **20 517 个不同程序**上通过（需要应用三个元数据没有声明的寄存器基址）。
* 所有缓存程序都带编译器戳 `2.0.6534.1`（2007 年 11 月 XDK）。

## 6. 渲染器实际在算什么（从常量名与反汇编）

### 光照与材质

* Blinn 着色（`eBlinn_Diffuse_Color0`、`eBlinn_Ambient_Color0`、`eBlinn_Specular_Color0`、`eBlinn_Translucent_Color0`）。
* 球谐环境光：`cvSHAmbContext`。
* 光照遮罩：`cvLightContext`、`cvLightMask`、`cvLightMaskMix`。
* 常量命名约定：`cv…` 常量向量、`cm…` 常量矩阵、`s…` 采样器、`e…` 材质/效果参数。
* 材质参数与 ASF `mats` 的浮点常量对得上（diffuse / ambient / specular 的顺序一致）。
* 视差：`eParallax_Offset_Scalar0`、`ParallaxMappingLo`；法线贴图：`NormalMap`、`NormalMapXYH`、`DecodeTexRGBE/L`。
* BRDF 片段：**Marschner**（头发）、**Ashikhmin–Shirley**（各向异性）、**Kajiya–Kay**（廉价头发替代）。ASF 的着色网络节点里也确实出现 `marschner`、`ashikhmin`，两边互相印证。
* 其他片段：`DoubleSided`、`Fresnel`、`LightMaskMixer`、`PlaneAbsorption`、`UVSetTransform`、`Lerp`、`BranchGTZBegin/End`。

### 阴影与后处理

* 阴影：`ShadowCascadeDepthProjector`、`ShadowCubeMapDepthProjector`、`ShadowDepthProjectorCond_PCF16 / _PCF9 / _PointSample`（级联 + 立方体 + PCF）。
* 色调映射：`cvReinhardWhite` —— **扩展 Reinhard，白点可调**。
* 泛光/混合：`cvBloomBlend`、`cvBias`、`cvGatherBlend`、`cvDitther`（原文拼写如此）。
* 景深：`cavDOF`、`poissonTb`（Poisson 圆盘核），`PoissonDOF` 有 `_Eclipse` / `_MaskTest` / `_Odd` 变体。
* 后期组合：`PostPrsCombinerCond_*` 覆盖暗角、胶片颗粒、抖动、色调映射。
* 失真：`DistortionFilter_*`（径向模糊、水波）。
* 粒子：15 个 `Particle_Cond*`。
* 天空/太阳：`cvSunDir`、`cvSunCol`、`cvZenithDir`。

### 水面模拟（memexport）

水面是一个**顶点着色器**：每个网格单元一个顶点，通过顶点纹理抓取采样前后两张高度场（`heightSampler`、`prevHeightSampler`），积分波动方程，把新高度和打包法线**写回内存**（Xbox 360 的 memexport，`cvExportAddr`、`cvExportNormal`），自身不画任何东西。几何通道再读回这些结果。参数：`cvWaveParams`、`cvGridSize`。

### 视频

`YTexture`、`UTexture`、`VTexture` 做 YUV 转换，服务于四容器里约 3.2 GB 的 WMV 视频。

## 7. AHSL

执行文件里三条路径：

```
e:\AHSLCacheUD4\AHSLProfileData
e:\AHSLCacheUD4\AHSLv2DiskCache
e:\AHSLCacheUD4\ahsl\
```

`E:` 是开发机盘符，`UD4` 是内部项目代号（本仓库就用它称呼这份基线）。**AHSL 是 tri-Ace 自己的着色语言层**；展开成什么没有明确记载，"Aska High-level Shading Language" 只是猜测。

关键事实是：**磁盘缓存随零售版一起发行**——116 MB、96 853 条记录，用 tri-Ace 在 PlayStation 2 上的半字 LZ77 压缩，字典被四年后的 Star Ocean 4 逐字节沿用。执行文件里还静态链接了微软整套 Xenon 微码编译器，说明开发期（很可能也在开发机上）会编译、缓存着色器变体。

## 8. 跨作品的渲染证据

* **Star Ocean 4**（2009）：固定库 60 个里有 **56 个逐字节相同**（连旧编译器戳都一样）；4 个不同的是"重投影运动模糊"，被 SO4 的 `cvVel` 家族替代。缓存格式同为 `AHSX`，版本 `0x0033.0000`，字典逐字节相同；11 679 个不同程序全部通过校验。变化的是 **key 的编码**。
* **Star Ocean 5**（PS3 2016）：执行文件里有 30 个随盘 AHSL 文件。
* **Anamnesis**（Android 2016）：库里有 147 处 `AHSL`。

## 9. 仍未解

* 30 720 字节的每碟表（`0x0000–0x77FF`，`0x100` 周期，不含指针）。与 SO4 对比后得知是 40 行 × 64 字的 (key, value) 对，key 属于引擎而非游戏，但 key 选择什么未知。
* 记录 key 的编码（推测是着色器片段排列/置换），以及它与 ASF 材质里的 shader program block 是否同一物。这是下一阶段的第一项测量。
* 记录 `+0x00` 的哈希、缓存 `+0x04` 的 mask、SO4 `0x102A1111` 顶点 magic 的 bit 4、SO4 的 `cvVel` 家族。
* 反汇编器仍有一处"双操作数标量通道选择"原样打印。
* Star Ocean 5 的 PS3 压缩方法仍未读。
