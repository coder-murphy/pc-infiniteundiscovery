# 08 场景资产格式

一个场景在 ASKA 里由六种格式共同描述：

| 格式 | 资源标签 | 作用 | 状态 |
| --- | --- | --- | --- |
| `ASF ` | `MESH` | 场景：几何、材质、内嵌纹理、节点树 | 已解 |
| `AIF ` | `IMG-` / `MAIF` / `RMD-` / `MTEX` | 纹理 | 已解（mip 链未解） |
| `AAF ` | `ANIM` | 动画：按节点命名的平移/旋转/缩放轨道 | 已解 |
| `ACF ` | `COLL` | 碰撞：骨架上的球树 | 已解 |
| `SNC-` | `SCE-` | 编译型场景脚本：生成谁、在哪、挂哪 | 容器与指令已解，语义大部分未解 |
| `NODE` | `NODE` | AI 导航网格 | 已解 |

一句话：**结构已经能从各个方向读通，缺的是"含义"**——253 个场景脚本 opcode 里只有 7 个知道做什么。

---

## 1. ASF——场景文件

`MESH` 解压后是 `ASF `，占 disc 1 `ud1.bin` 1 812 个压缩块中的 916 个。它不是"一个网格"，而是一个**自包含的小场景**：几何、材质、材质引用的纹理、以及把它们串起来的命名节点树。

### 块树

每个块 16 字节头（大端）：tag、内容大小（含头）、零（退化回链）、到下一个兄弟的步长（0 表示等于内容大小）。

```
ASF                    文件
  ao__                 一个对象：包围盒 + 它需要的一切
    AIF                内嵌纹理
    ml__ / mats        材质
    bnpl               骨骼池：节点号
    mess               一个网格
      bnpi             本网格的骨骼池切片
      idxl             三角形索引
      vlas             顶点
    rl__ / rnel        着色网络
    ptcl / pprn / pani 粒子
  tree                 节点图
    attr               一个命名节点
  modf / extl          小，未读
  eof_                 结束
```

子块不一定紧跟头：`ao__` 先有 `0xA0` 字节 payload，`tree` 有 `0xB0`，`mess` 有 `0x10`。读取器的做法是尝试每个 16 字节偏移，取"能精确铺满剩余部分"的那个，因此不依赖这张表。

### 节点树

`tree` 里每个节点是一个 `attr`，开头 16 字节 NUL 填充名字，全部是美术在建模软件里的命名：

```
ROOT  R:M:SK_WEP01 .. R:M:SK_WEP09  R:M:CAPEL_WEAPON
ROOT  camera1_group  camera1  camera1_aim  POS_ROOT  POS_Pad1  POS_Pad2
      SQ  TM  R  MS  Tri_ace
```

`Capell` 是主角，`SK_WEP01–09` 是他的武器组；也有 Maya 默认名（`pPlaneShape6`、`polySurfaceShape`）。

**精确铺满规则的例外**：369 个模型文件里有 86 个在最后一个 `attr` 之后还跟一段"不是块"的数据（144–3 600 字节），精确铺满测试会因此拒绝整棵树。正确做法是**信任头里的节点数**：`attr` 从 body + `0xB0` 开始，正好那么多块，后面是尾巴。这样可读节点图从 283 个文件提升到 **369 / 369**，节点数从 19 328 到 **23 979**。

外部校验：900 个动画的常量通道应复现场景静止姿态；修复前后多纳入 26 346 个通道，吻合率仍保持 99.5%。

### 顶点与蒙皮

* 全部 14 618 个网格的所有属性可解码。
* 法线与周围三角形中位数偏差 **2.3°**；蒙皮权重在 **2 919 607 个顶点**上 100% 求和为 1。
* 顶点一字节骨索引经过 `bnpi` / `bnpl` 到 `tree` 节点；**369 个文件全部**用自己的树，不存在共享骨架资源。261 个蒙皮对象全部通过。
* 盒体校验：3 855 个对象、130 万三角形，98.4% 复现文件自报的包围盒；59 个不吻合的多为宝箱与形变目标（几何会动，盒可能描述另一个姿势）。

### 材质

* 每个网格带一个有符号位移指向材质；**4 176 个**被测网格全部命中。
* 材质用 8 字节 key 引用纹理，和 AIF 头里的 asset id + asset number 完全一致；ASF 语料 2 892 个引用中 **2 611 个**解析到同文件内嵌纹理。
* `mats` 的浮点常量正好对应 `eBlinn_Diffuse/Ambient/Specular_Color0` 等常量名。
* 导出：`asf.py obj` 输出带 MTL 和已解码 PNG 的 OBJ。

### 未读部分

`ptcl`/`pprn`/`pani`（粒子）、`modf`、`extl`、`PAIF`、`AAIF`、`ACHF`、`glbl`、`mdfr`、`anim`；`tree` 之后的尾巴（大角色骨架以 32 字节记录点名骨链并带阻尼/刚度浮点，最自然解读是头发/裙摆模拟）。

## 2. AIF——纹理

所有纹理都是 `AIF ` payload，标签有四种，格式相同。它是一层薄包装，里面是**已经是 Xbox 360 GPU 内存布局**的纹理——读它主要是撤销主机纹理转换器做的事：平铺地址混淆（swizzle）与字节序。

* 头 4096 字节，`0x1000` 起是像素。
* 格式码是 tri-Ace 自己的枚举：`0x50` DXT1、`0x52` DXT3（显式 alpha）、`0x54` DXT5（插值 alpha）、`0x48` A8R8G8B8、`0x46` A4R4G4B4。DXT 的 3/5 判定靠解出来比对，并在 3 695 个半透明块上 100% 胜出。
* pitch 不是 `宽 × 元素字节`，而是宽度向上取整到 **32 元素**；数据高度同理，因为 GPU 以 32×32 元素为瓦片寻址。960×540 的 DXT1 是 240×135 块，但按 256×160 存。
* `0x20` 的 4 字节是资产标识：前缀 `CH` 角色、`BG` 背景、`EF` 特效、`PG` 界面；`0x20` + `0x24` 合起来是材质引用的 key。
* 字节序：A8R8G8B8 直接是 A/R/G/B；16 位字段组成的 DXT 与 A4R4G4B4 需要每两字节互换，否则颜色错但图像仍"干净"。

校验：disc 1 `ud1.bin` 的 **220 个图像、1.509 亿像素全部解码无失败**。

`RMD-` 是**消息资源**：AIF 是字体图集（拉丁、假名、汉字轮廓字形），同一 SLZ 流后半段是文本，还能看到构建工具版本串 `MessageConvertLib_1.0.0.0`。`IMG-` 是 UI（标题 logo 960×540、按键图集、伤害数字）。`MTEX` 是材质纹理，含把四种地面/墙面法线打包进一张 1024×1024 的图集。

未解：mip 链（Xbox 360 把小 mip 打包进共享瓦片）、`0x34` flags。

## 3. AAF——动画

`ANIM` 解压后是 `AAF `。disc 1 `ud1.bin` 有 **5 718 个、278 MB**，是按数量最多的资源；1505 个 `MESH` 居次。

AAF 不独立存在：它驱动 ASF 的节点树，记录名就是 `attr` 名，常量通道的值应等于节点的静止姿态。这个外部关系同时是**通道身份的来源**和**解码校验**。

* 头 0x24 字节；计数与大小都在 32 位槽的**低半字**（某些文件高半字非零，按 32 位读会走出记录）。
* 四个区域：records、block table、constant curves、keyframe blocks。
* 一条 record 是一个节点；track 是它的一个通道。通道号：**5 平移、6 旋转、7 缩放**。
* flags：`0x20` 关键帧在块里；`0x80` 常量在常量区；`0x400` 打包四元数无切线。
* 旋转是 **48 位打包的轴角四元数**，三个字段都是"以直角为单位的分数角度"。
* 900 个样本 payload 全部解析并通过内部校验；4 931 条动画轨道与块表完全一致。
* 静止姿态复现：平移 86 246 / 86 642（99.5%）、旋转 91.9%、缩放 99.5%。
* 另有 `SKAC` 作为角色的额外动画包（见 [07](07-资源容器与压缩.md)）。

未解：头 `+0x20` 大于文件大小的字（像缓冲区大小）、动画轨道 `+0x14` 的三个浮点（像时间窗）、时间单位、5/6/7 之外的通道号（14、16、18、22、45……出现在灯、发射器、相机）、`+0x12` 的语义字节。

## 4. ACF——碰撞

`COLL` 解压后是 `ACF `，disc 1 有 **972 个、2.7 MB**，是最小且读得最完整的 Aska 格式之一：一个套在球/立方体/胶囊上的球树，不压缩，美术的 Maya 名字还在。

* 头 0x30；`+0x28` 是全文件最高的 `center.y + radius`，972 个全部精确，是"天花板高度"。
* 组记录 0x40 字节：包围球 + 32 字节名字 + 类型（0 分支 / 0x100 叶）+ 掩码 + 5 个槽。
  * 分支的槽是子引用，`0xFFFF` 结束；bit `0x8000` 表示子节点是叶。
  * 从组 0 顺着槽能**恰好一次到达文件里每个组**，在 522 个有分支的文件上成立——槽构成生成树。
  * 叶用 `(first, count)` 精确划分图元数组，972 个文件全部成立。
* 图元记录 0x30：名字、形状（**0 球 / 1 立方 / 2 胶囊**）、索引、数据偏移、掩码。
* 图元数据：中心 + 包围半径 + 形状参数。全语料 3 767 胶囊、2 625 立方、1 925 球。
* **组名就是骨骼名**，与 ASF 节点树、AAF 记录同名：1 269 个组名中 947 个在相邻场景的节点树里，196 个文件里 179 个全中。因此球树就是骨架，每个组的球在它自己的骨骼空间里——这也解释了为什么分支的球不包围子球（骨骼变换在 ASF 里，不在这里）。

未解：图元 `+0x28` 的 u16、碰撞掩码各位含义、`+0x2C`。

## 5. SNC——场景脚本

`SCE-` 解压为 `-CNS00.3`（`SNC-` 版本 3.00）。disc 1 44 个、disc 2 `ud1.bin` 17 个，共 **61 个 payload、30 MB**。它回答"模型完成之后，是什么在驱动它们"：场景生成哪些对象、每个是什么资产、站在哪、挂哪根骨头、用哪盏灯和哪个阴影、过场里怎么动。

执行文件 RTTI 印证：`CSceVar`、`sce::Var`、`CSceSceneController`、`CSceDelayTask`、`CSceSpecialProcess_01Tsunami`、`CSceSpecialProcess03_VeszpremMirrorRoom`、`CSceSpecialProcess_02OgreJump`——一个场景控制器、一个等待任务，以及按地点命名的硬编码演出。

### 容器

0x30 字节头，**所有偏移与长度按 32 位字计数**（读之前必须知道）。四个区：code、data、strings、entries，首尾相接、四字对齐。头里的顺序不一定等于文件顺序（61 个里有 15 个 entries 在 strings 前），所以文件结束取 `max(offset + length) * 4`。

### 指令

每条指令 4 字节头（操作数字数，两两计 → 恒偶数；opcode）+ 8 字节操作数。

* 走完 code 区恰好落在末尾，61 个全部成立。
* **253 个不同 opcode，每个的 operand 数唯一**（420 532 条指令）；217 个还有唯一的 operand 种类序列，其余 36 个只是在同一槽位换种类——这正是 tagged value 的用途。
* 每个文件以四个零字（opcode 0）开头，以 `0x0005` 结尾；`0x0005` 也是正文里最常见的零操作数指令，即终止符。

### 操作数 `sce::Var`

8 字节：1 字节 kind（可打印 ASCII 字母）、1 字节 sub-kind、2 字节 aux（`0x0100` = 浮点立即数）、4 字节值。

| kind | 含义 | 落点 |
| --- | --- | --- |
| `$` | 字符串，字符串区的**字节**偏移 | 5 035 / 5 035 |
| `@` | 数据块，data 区的**字**偏移 | 413 467 / 413 467 |
| `&` | 代码地址，code 区的**字**偏移 | 18 666 / 18 666 |
| `n` | 立即数 | — |

`&` 有两种读法且都精确：16 个 opcode 按绝对字偏移；opcode `0002` / `0003` 按"相对自身、有符号"，5 182 个全部落点；若按绝对读，4 949 个只对 679 个。

### 语义

7 个 opcode 已识别：场景生成什么、站在哪、挂哪根骨头、用哪盏灯和哪个阴影。其余 246 个只知道 number、arity、operand 种类。两个抓手：19 个签名以 `@@nn` 结尾的 opcode 明显共享尾部结构（88 690 / 420 532 条）；`0133` 在尾部前放两个四元数，是旋转补间。

## 6. NODE——导航网格

每个带 `SCE-` 的场景归档都一一配一个 `NODE`。没有 ASCII magic，开头是常量 `0x0131F119`，因此从第 3 次会话一直挂到第 11 次才读通。

它是**可行走地面**：切成凸多边形的楼层、多边形之间的门、以及预先算好的过路代价。

* 61 个 payload 全部解析。
* 53 987 节点、55 140 链接、32 854 分区。
* 引用编码是 `index << 8`（低字节含义未知）：`word >> 8` 对 109 127 个节点/链接全部等于其位置。
* 冗余校验：链接的边落在两侧多边形上 110 202 / 110 202；路线代价等于两个门中点距离 167 316 / 167 316；路线指向远端节点 167 316 / 167 316。
* 99.86% 的链接被两侧列出；97.64% 多边形在 XZ 平面凸；99.99% 绕向一致。
* 外部校验：同归档场景脚本的对象生成点 **99.44%** 落在自己的 nav mesh 内。
* 802 个节点只有两个顶点（退化）；gate 组、尾部表未解。

## 7. 这些格式如何咬合

```
MESH  → ASF ─┬─ tree(attr) ← AAF 记录按名字驱动
             ├─ AIF 内嵌纹理 ← mats 用 8 字节 key 引用
             ├─ bnpl/bnpi → 顶点骨索引 → tree
             └─ mats 浮点常量 ← 着色器 eBlinn_* 常量

COLL  → ACF 组名 = 骨骼名，与 ASF tree / AAF 记录同名
SCE-  → SNC 生成对象、指定资产/位置/骨骼/灯/阴影
NODE  → 同一归档里的 nav mesh，AI 用来寻路
SKAC  → 角色额外动画包，骨架在相邻模型归档
```

这也是"场景在结构上已从各个方向读通"的含义：几何、材质、纹理、骨架、动画、碰撞、驱动脚本、导航网格，全部能互相对上。未读的是**语义**与少数块。
