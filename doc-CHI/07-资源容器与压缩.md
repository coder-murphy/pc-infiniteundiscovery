# 07 资源容器与压缩

## 1. 光盘布局

两张盘都是 XGD2，镜像大小 7 835 492 352 字节（Redump 风格完整镜像，含前端 DVD-Video 兼容区）。游戏分区基址 `0x0FD90000`。

| | Disc 1 | Disc 2 |
| --- | --- | --- |
| 文件系统根扇区 | 701 980 | 1 774 503 |
| 卷时间戳（UTC） | 2008-07-08 20:52:54 | 2008-07-08 21:19:37 |
| `ud1.bin` 大小 | 2 207 584 256 | 3 217 651 712 |
| `ud2.bin` 大小 | 2 800 330 752 | 3 289 788 416 |
| `default.xex` | 11 055 104 | 11 055 104 |

文件系统只有 4 个文件 + 1 个目录。`$SystemUpdate` 是微软要求每张盘都带的仪表盘更新，与游戏无关。

`ud1.bin` 与 `ud2.bin` 分工按**种类**而不是按地区：`ud1.bin` 放全局内容（5 700+ 动画、1 500+ 模型、1 200+ 声音、217 个 `WEAP`），`ud2.bin` 放地区内容（以 `EPAC`/`APAC` 打包块和 `MTEX` 为主，分 40 组）。

## 2. XDVDFS：只读文件系统

Xbox / Xbox 360 光盘文件系统。故意做到极简：没有分配位图、没有碎片、没有日志，每个文件都是连续扇区；目录不是列表，而是**序列化成一段连续字节的平衡二叉搜索树**。

关键点：

* 扇区 2048 字节；卷描述符在分区基址 + `0x10000`（第 32 扇区）。
* 魔数 `MICROSOFT*XBOX*MEDIA` 出现在扇区首尾 20 字节，两处都检查可以排除"碰巧开头对"的假分区。
* 目录项 4 字节对齐；左右子树指针以 **4 字节为单位**；根在偏移 0。
* `0xFF` 填充会被解码成"左=右=0xFFFF、起始扇区=0xFFFFFFFF"，要当终止符。
* 子指针 0 有歧义（既是根偏移，也被一些刻盘工具当作"无子节点"）；把 0 当"无"是安全的，能防止绕回根。
* 排序不是 ASCII 序，而是"先长度、后字节值"的忽略大小写比较。

卷时间戳是 Windows `FILETIME`（1601 年起的 100ns），实际记录刻盘时间，是很少被篡改的发行日期证据。

## 3. NORM / MRON：资源归档

游戏几乎所有内容都在 `MRON00.2` 归档里。把 4 字节组反过来读就是 `NORM` 版本 `2.00`；归档内所有类型标签也遵循同样的反转规则：原始字节 `HSEM` = `MESH`，`MINA` = `ANIM`，`XETM` = `MTEX`，`AERA` = `AREA`。这是大端数据里唯一的例外（payload 本身是大端）。

### 头（32 字节，大端）

| 偏移 | 大小 | 字段 |
| --- | --- | --- |
| `0x00` | 8 | `MRON00.2` |
| `0x08` | 4 | 条目数 |
| `0x0C` | 4 | 数据区起始对齐 |
| `0x10` | 4 | group id |
| `0x14` | 12 | 保留零 |

### 条目表（`0x20` 起，每条 32 字节）

| 偏移 | 大小 | 字段 |
| --- | --- | --- |
| `0x00` | 4 | 类型标签（反转 FourCC） |
| `0x04` | 2 | 组内子索引 |
| `0x06` | 2 | group id |
| `0x08` | 4 | 大小 |
| `0x0C` | 4 | 相对归档头的偏移 |
| `0x10` | 16 | 保留零 |

### 布局推导

```
data_start = align_up(0x20 + count * 32, alignment)
total      = align_up(max(entry.offset + entry.size), 2048)
```

因为 `total` 能只靠头算出来，整个容器可以**没有全局索引**地顺序走完。观测到的对齐是 `0x10`、`0x40`、`0x800`；`0x800` 总是打包数据，符合"按扇区直接读"的行为。

`group id` 把归档串起来：同一个游戏区域的归档共享 group id，并连续出现（通常是"网格+纹理+场景"归档，紧跟一个较粗对齐的 `APAC`/`EPAC` 归档）。

`ud2.bin` 以 `EPAC`（3 340 个、1.19 GB）、`MTEX`、`APAC` 为主，另有 40 个 `SCE-`/`NODE` 对。

payload 的 magic 才说明"它是什么"，标签说明"它是干什么用的"，两者要分开看。嵌套归档有六种：`EPAC`、`SEEK`、`TTEX`、`WEAP` 直接嵌套，`SKAC`、`APAC` 在 SLZ 之后嵌套。`MTEX` 有时也是嵌套归档（disc 1 `ud1.bin` 里 46 个）。

`SKAC` 解开后是 **250 个 `ANIM` + 161 个 `MESH` + 129 个 `SIG-` + 90 个 `COLL`**，是角色的"溢出动画包"。它驱动的骨架不在包内，而在相邻归档；15 个 `SKAC` 组里有 13 个，紧邻其下方的模型归档是全部 160 个候选里最匹配的。

## 5. 压缩：SLZ 与 XCompress

`SLZ` 是游戏里最古老的东西，而且**比引擎还老**：1998 年 Star Ocean: The Second Story 的 PlayStation 盘上就有，2016 年的 Star Ocean 5 还在用，横跨三种 CPU、三种头版本。

Xbox 360 上的 `SLZ` 是 tri-Ace 的 **24 字节包装**套在微软 **XCompress** 流外：

### tri-Ace 包装（24 字节）

| 偏移 | 大小 | 字段 |
| --- | --- | --- |
| `0x00` | 3 | `SLZ` |
| `0x03` | 1 | 版本，全部为 4 |
| `0x04` | 4 | 头大小 `0x20` |
| `0x08` | 4 | 压缩大小（从 `0x18` 起算） |
| `0x0C` | 4 | 解压后大小 |
| `0x10` | 4 | 零 |
| `0x14` | 4 | 一 |

### XCompress 流头（48 字节，从 `0x18`）

| 偏移 | 大小 | 字段 |
| --- | --- | --- |
| `0x18` | 4 | 魔数 `0x0FF512EE` |
| `0x1C` | 4 | 版本 `0x01020000` |
| `0x20` | 4 | context flags |
| `0x24` | 4 | flags |
| `0x28` | 4 | 窗口 `0x20000`（128 KB） |
| `0x2C` | 4 | 压缩分区 `0x80000` |
| `0x30` | 8 | 解压后大小 |
| `0x38` | 8 | 压缩大小 |
| `0x40` | 4 | 解压块大小 `0x20000` |
| `0x44` | 4 | 流内最大压缩块 |
| `0x48` | | 块表：每块 4 字节压缩大小 + 数据 |

块表自校验：走完恰好落在压缩区末尾，遇到的最大块大小总等于 `0x44` 的值。

含 SLZ 的条目按 `entry size = align_up(compressed, 4) + 24` 填充。

### 状态

disc 1 `ud1.bin` 的 **1 812 个块全部解压无错**，解压后 1.88 GB。每段能自报长度的 payload 都与解压结果一致——这是独立于解压器的校验。

### 陷阱：不是每个 SLZ 块都压缩

有少数 payload 的 SLZ 头里"压缩大小 == 解压大小"，后面根本没有 XCompress 流，payload 就是从 `0x18` 起的声明字节数。disc 1 `ud2.bin` 的 40 个 `SCE-` 里有 7 个如此，全部小于 200 字节。`mron.py --decompress` 会把它们报成"0x18 处没有 XCompress magic"的失败——先认出这一类，再怀疑解压器。

## 6. SLZ 的三个头版本与 PlayStation 编码

| | PS1–PS2，1998–2006 | Xbox 360，2008–10 | PS3，2016 |
| --- | --- | --- | --- |
| `0x00` | `SLZ` | `SLZ` | `SLZ` |
| `0x03` | **方法**：0 存储，1–3 压缩 | 恒为 4 | **方法**：0 存储，1–3 压缩 |
| `0x04` | 压缩大小 | `0x20` | `0x00010025` |
| `0x08` | 解压大小 | 压缩大小 | 压缩大小 |
| `0x0C` | 零 | 解压大小 | 解压大小 |
| `0x10` | payload | 零 | 零 |
| `0x14` | | 一 | `0x20` |
| `0x18` | | XCompress 流 | `0x00400001` |

第一列覆盖五张盘、八年，**没有任何字段移动**。

PlayStation 上的方法 1、2、3 是**同一个 LZ77 的三种设置**，不是三个编解码器：

* **方法 1**：经典字节 LZ77，带结束标记；
* **方法 2**：同样的 LZ77，把长度半字节的最高槽用于"重复串"而不是"匹配"，去掉结束标记，用声明的输出大小作为停止条件；
* **方法 3**：同样的 LZ77，所有单位加宽为**半字**，保留结束标记。

跨 1998、1999、2003、2005、2006 五张盘，**62 167 / 62 167 块全部解码**；方法 2 的 36 598 块还全部把输入消耗到最后一个字节。

`SLE` 从 2003 年起一直和 `SLZ` 并排出现，它不是编解码器，而是**加密信封**：明文解出后它把自己的 magic 改写成 `SLZ`，然后落入同一个方法分发表。1998/1999 的盘上没有 `SLE`，所以这对名字有两个生日。

## 7. 归档之间的空隙

不是所有字节都是归档：

| 种类 | 识别方式 | 规模 |
| --- | --- | --- |
| ASF/WMV 视频 | GUID `75B22630-668E-11CF-A6D9-00AA0062CE6C` | 四容器约 3.2 GB |
| AAC 音频库 | 连续 `AAC ` 容器 | disc 1 约 289 MB + 135 MB |
| SLZ 块 | `SLZ` 头 | 少量 |
| AHSX 缓存 | `AHSX` 头 | 9 个、116 MB（曾被误算为视频） |
| 未分类 | — | disc 1 `ud1.bin` 开头 `0x16000` 的一部分 |

`ud1.bin` 开头的 `0x16000` 现已拆成：`0x0000–0x77FF` 未知表（30 720 字节）、`0x7800–0xBCC1` 一个 AHSL 缓存、`0xC000–0x147FF` 固定着色器库（60 个）、之后零填充。只剩第一段未解。
