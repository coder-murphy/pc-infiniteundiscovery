# 02 运行时核心子系统

本章整理 `Aska::` 命名空间所暴露的运行时能力。**证据等级**：类名存在是确证的；"它怎么工作"是从名字、接口命名和同镜像字符串推断出来的。凡推断，均按"可能/暗示/推测"标注。

## 1. 应用与任务调度

```
Aska::App  Aska::Task  Aska::FiberTask  Aska::Thread  Aska::MemoryManager
```

* `App` 是应用对象；`Task` 是最小调度单元；`FiberTask` 把任务放在纤程上执行；`Thread` 是硬件线程封装。
* 纤程与线程并存，暗示**协作式任务调度**：大量小任务在少量硬件线程上按纤程切换，这是主机引擎常用的做法（避免线程上下文开销）。
* 字符串 `Aska::ObjectManagerWorkerThread(%d)` 说明对象管理器自己起工作线程，对象更新/流式装载可能不在主线程完成。
* `MemoryManager` 与自研容器库（`TArray`、`TList`、`TSmartPointer`、`List`、`LinkElement`、`INotify`）配套，说明内存分配被引擎完全接管。整个二进制只有 9 个 `std::` 类型。

## 2. 资源流式加载

```
Aska::ResourceManager
  ::LoadNotify
  ::IntermediateLoadNotify
  ::DecompressNotify
```

三段通知接口分别对应**加载、中间加载、解压**三个阶段。可以还原出一条可能的流水线：

1. 请求一个资源；
2. 从容器/NORM 读入原始块（`LoadNotify`）；
3. 中间态/部分可用（`IntermediateLoadNotify`）；
4. SLZ 解压完成（`DecompressNotify`），交给具体文件处理器。

这与数据侧的观察吻合：`MESH`、`MTEX`、`SCE-`、`SKAC`、`APAC` 都以 `SLZ` 包装（见 [07](07-资源容器与压缩.md)）。资源管理器在引擎里，文件格式解析在下述 handler 里，两层分离。

## 3. 文件处理器

```
Aska::AofHandler   Aska::DirectAofHandler   Aska::AofObject
Aska::AsfHandler
Aska::AcfPrimitiveData_capsule / _cube / _sphere
```

* `AsfHandler` 对应 `ASF ` 场景文件；`AcfPrimitiveData_*` 对应 ACF 的三种碰撞体。
* `AofHandler` / `AofObject` 说明还有一类 **AOF** 对象文件。AOF 在引擎里被点名三次，但**从未作为光盘 payload 的 magic 出现**。ASF 里承载单个对象的块叫 `ao__`，与 `AofObject` 只是名字相似，这是目前唯一的线索，尚不能证明。
* 这套"格式 = 处理器"的设计与 `A…F` 命名一致：AAF 动画、ACF 碰撞、AIF 图像、ASF 场景。

## 4. 渲染与后处理（概览）

渲染主链路由以下类构成：

```
RenderPassManager / RenderPassManagerList
RenderableObject / RenderablePrimitive / Primitive / PrimitiveBufferXe
ShadowManager / FrustumObject
TextureHandler / ITextureHandler / TextureModifier / TextureModifierManager
```

后处理：

```
BackBufferEffect / CameraFilter
BrightnessContrastFilter / MonotoneFilter
FramePersistanceEffect / CrossFader
```

这里能读出的能力面是：多通道渲染、可渲染对象/图元抽象、Xenos 专用图元缓冲、阴影管理、视锥对象、纹理修饰（可能是运行时生成/替换纹理），以及后缓冲效果链。具体着色器与常量表见 [05-渲染与着色](05-渲染与着色.md)。

## 5. 相机

```
Aska::Camera  Aska::CameraSynchronizer  Aska::Camera::AFPoint
```

* `Camera` 是相机基类；`CameraSynchronizer` 暗示多个相机（游戏相机、过场相机、UI 相机）之间的同步/切换。
* `AFPoint` 大概率是自动对焦参考点（Auto Focus Point）；这与后处理里的景深（DOF）家族能对上。
* 数据侧也有印证：ASF 节点树里有 `camera1_group`、`camera1`、`camera1_aim`，AAF 记录里同样有相机通道。

## 6. 动画与层级

```
Aska::Joint  Aska::HierarchicalObject  Aska::HierarchicalObjectContainer
Aska::IAnimatable  Aska::AnimatableLinkElement  Aska::AimingObject
```

* `Joint` 是关节；`HierarchicalObject` 是可挂接的层级对象；容器管理一组层级对象。
* `IAnimatable` / `AnimatableLinkElement` 把"可动画"做成接口/链表元素，暗示动画通道通过链接挂到对象上，而不是每个对象自带一整套动画状态。
* `AimingObject` 是瞄准对象，可能与战斗/相机朝向有关。
* 数据侧：ASF 的 `tree` 节点树 + AAF 的按节点命名的轨道，正好是这套层级动画模型；一个顶点经一字节骨索引 → `bnpi`/`bnpl` → `tree` 节点（见 [08](08-场景资产格式.md)）。

## 7. 物理与风

```
Aska::Dynamics  Aska::DynamicsForceEmitter
Aska::DynamicsWorldWind    ::_WorldWind
Aska::DynamicsOmniWind     ::_OmniWind
Aska::DynamicsCircleWind   ::_CircleWind
```

* `Dynamics` 是动力学入口；`DynamicsForceEmitter` 是力发射器。
* 三种风场：全局风、全向点源风、圆形风。每种都带一个嵌套实现结构，说明风场是独立可组合的对象，而不是一个标量参数。
* 这套系统在 2008 年的作品里算重投入。它与 ASF 里尚未解读的尾部块可能有关——那些块在大型角色骨架上会以 32 字节记录点名骨链（`R:M:SK_A_LtHipFt` 等），并带类似阻尼/刚度的浮点数，最自然的解读是头发/裙摆模拟。目前**尚未解码**（见 [12](12-现状与未解问题.md)）。

## 8. 碰撞与地形

```
Aska::CollisionHandler  Aska::ILandscapeConstraint
```

* `CollisionHandler` 负责碰撞查询；`ILandscapeConstraint` 是地形约束接口（可能是把角色约束在地面/斜坡上的策略接口）。
* 数据侧：ACF 是"球树套球/立方体/胶囊"，挂在骨架上（见 [08](08-场景资产格式.md)）；NODE 是可行走地面的导航网格。两者的职责不同：ACF 用于精确碰撞，NODE 用于 AI 寻路。

## 9. 自研容器库

```
Aska::TArray<T, N>  Aska::TList<T>  Aska::TSmartPointer<N>
Aska::List  Aska::LinkElement  Aska::INotify
```

* 固定容量数组、链表、智能指针、侵入式链表元素、通知接口。
* 这与"引擎完全掌控分配"的推断一致；也解释了为什么 `std::` 只有 9 个类型。
* `INotify` 与资源管理器的三段 Notify 可能是同一套观察者模式的复用。

## 10. 小结

| 子系统 | 已确证 | 仅推断 |
| --- | --- | --- |
| 调度 | 类与线程名字符串 | 纤程调度策略、任务粒度 |
| 内存 | 管理器与容器库 | 分配器实现 |
| 资源 | 三段通知接口 | 流水线阶段与线程归属 |
| 文件 | 三类 handler | AOF 的实际用途 |
| 渲染 | 类清单 | 通道顺序、对象批次 |
| 相机 | 类清单 + 数据侧相机节点 | 同步策略、AFPoint 用法 |
| 动画 | 接口/链表 + 数据侧轨道 | 求值顺序 |
| 物理/风 | 类清单 | 与 ASF 尾部块的对应 |
| 碰撞 | 类清单 + 数据侧 ACF | 查询结构与 mask |
| 容器 | 类型清单 | 具体实现 |

这些"仅推断"项正是 [12-现状与未解问题](12-现状与未解问题.md) 里仍然开放的部分。
