# 03 AI 系统

## 1. 规模与总体结构

RTTI 里 AI 相关类型合计约 **285** 个：

| 分组 | 数量 |
| --- | ---: |
| `AI…` 框架 | 138 |
| `AIBehavior_…` 行为 | 94 |
| `AIFsm_…` 状态机 | 33 |
| `CAI…` 支持类 | 20 |

结构是**行为树套在有限状态机上**，两者通过泛型适配器桥接：

```
AIObjectInterfaceBridge<AIBehavior, AICompositeBehavior>
AIObjectInterfaceBridge<AIFsm, AIBrainBase>
AIObjectInterfaceBridge<AIObjectBase, AIBrainBase>
```

可以读出的模型是：`AIBrainBase` 是"大脑"基类；行为树（`AIBehavior` / `AICompositeBehavior`）与状态机（`AIFsm`）都能接到同一个大脑接口上。也就是说，AI 可以用行为树组织常态决策，用 FSM 管理整体状态（战斗、警戒、逃跑等），二者不是二选一。

## 2. 寻路

A* 寻路，支撑类型都在引擎/游戏命名空间里：

```
CAISearchAStar      它的 RouteData
CAIAStarPoint       CAStarAlgorithm<CAIAStarPoint>
CAINodeLink         CAIPartition       CAIRoutePoint
CPartitionOptionDoor  CPartitionOptionToggle
CPartitionOptionTroopPlayer  CPartitionOptionTroopEnemy
```

* `CAISearchAStar` 是搜索器，`CAStarAlgorithm<CAIAStarPoint>` 是泛型 A* 实现。
* `CAIPartition` 是空间分区；`CAINodeLink` 连接相邻多边形；`CAIRoutePoint` 是路径点。
* `CPartitionOptionDoor` / `Toggle` 说明分区可以带门或开关；`TroopPlayer` / `TroopEnemy` 说明门/开关可对玩家方或敌方分别生效。这是一套"阵营感知"的导航约束。
* 数据侧对应 `NODE` 资源（见 [08](08-场景资产格式.md)）：导航网格由凸多边形组成，链接带**预计算的过路代价**，门作为特殊链接。

## 3. 感知

```
CSenseeObject
CSensorResult::foundInfo
```

* `CSenseeObject` 是被感知对象；`CSensorResult::foundInfo` 是感知结果里的"发现了什么"。
* 这说明感知系统产出结构化结果（目标、位置、信息），而不是简单的距离判断。具体传感器种类（视觉/听觉）尚未从名字中读出。

## 4. 状态机清单

状态机以职责命名，同时把游戏内容也点了出来：

```
AIFsm_Battle     AIFsm_Camp       AIFsm_Caution     AIFsm_Escape
AIFsm_Order      AIFsm_Normal     AIFsm_NoMesh      AIFsm_PigeonEscape
AIFsm_AvoidTsunami  AIFsm_EscapeVillager
AIFsm_BattleSeiryu  AIFsm_Ex01_QueenSpider  AIFsm_Ex01_HornBear
AIFsm_Ex01_Harpy    AIFsm_Ex01_GremrinFish  AIFsm_Ex01_Kandelaar
AIFsm_Ex01_Sarande_A  AIFsm_Ex02_QueenSpider
AIFsm_Niedzielan_Action01
```

可读出的分工：

* `Normal` / `Caution` / `Battle` / `Escape` —— 通用战斗状态循环；
* `Camp` / `Order` —— 营地与指令（可能与同伴 AI 的编队/命令有关）；
* `NoMesh` —— **没有导航网格时的兜底状态**。它的存在反过来证明：其余 AI 默认都假设有 nav mesh；
* `AvoidTsunami` / `EscapeVillager` / `PigeonEscape` —— 为单个场景写的演出型行为（海啸、村民逃跑、鸽子）；
* `Ex01_*` / `Ex02_*` 与 `Niedzielan_Action01` —— 具体敌人/Boss 与具体地点（Niedzielan 是游戏内地名）的特化状态机。

这实际上从 AI 侧恢复了游戏的一部分内容清单，尤其是 Boss 名单（Queen Spider、Horn Bear、Harpy、Gremrin Fish、Kandelaar、Sarande）。

## 5. 导航网格（NODE）

`NODE` 是 AI 的"可行走地面"数据，与每个 `SCE-` 场景脚本一一配套（disc 1 44 对，disc 2 的 `ud1.bin` 17 对）。

| 项 | 数值 |
| --- | --- |
| 解析 | 61 / 61 |
| 节点 / 链接 / 分区 | 53 987 / 55 140 / 32 854 |
| 自引用 index == 位置 | 109 127 / 109 127（100%） |
| 链接边落在多边形上 | 110 202 / 110 202（100%） |
| 路线代价 == 两个传送门中点距离 | 167 316 / 167 316（100%） |
| 链接被两侧列出 | 55 062 / 55 140（99.86%） |
| 分区盒是 XZ 包围盒 | 32 804 / 32 854（99.85%） |
| 多边形在 XZ 平面凸 | 51 930 / 53 185（97.64%） |
| 多边形绕向一致 | 53 180 / 53 185（99.99%） |
| 场景脚本的生成点落在 nav mesh 内 | 99.44% |

其中"链接边是两侧多边形的公共边"和"路线代价等于两个门中点距离"是**冗余存储**：文件里另存了一份可直接由几何算出的数。这两项在 27 万多例里全部对上，是格式被读懂的最强证据。

参考实现：`index << 8` 加低字节的引用编码；低字节含义仍未知。多边形只有两个顶点的节点有 802 个（可能退化）。门槛/开关组、尾部表也仍未解。

## 6. AI 与场景脚本的关系

* `SCE-` 脚本负责"场景里放什么、放在哪、挂在哪根骨头、用哪盏灯和哪个阴影"（见 [08](08-场景资产格式.md)）。
* `NODE` 负责"AI 能走哪里、怎么走"。
* 两者在同一归档里一一配套；脚本里的对象生成点有 99.44% 落在自己的 nav mesh 内，这是跨格式的外部校验。
* 引擎侧的 `AIFsm_NoMesh` 则说明 AI 在不具备 nav mesh 时切到兜底逻辑。
