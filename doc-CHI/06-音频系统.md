# 06 音频系统

## 1. 结论

游戏里每一个声音都在一个 **`AAC ` 容器**里——音效、语音、音乐。它**不是 MPEG AAC**：四个字节是 tri-Ace 自己的，里面装的是 **Xbox Media Audio（XMA2）**。名字撞车与 `ASF ` 一样，只是三个字母相同。

引擎侧线索：执行文件里有调试字符串 `AAC version problem  BGM ID=%d`，另有 `AirPlayAac - %d` 与 `WavetableSynth %i`——后者说明除采样音频外还有**波表合成器**。

## 2. 声音在哪

两个位置，第二个是音乐找了很久的原因：

1. **作为 `SOND` 资源**：disc 1 `ud1.bin` 有 1 275 个，其中 445 个是空槽（16 个零字节），其余 830 个是容器，每个装 1 到数百个声音：脚步、开门、法术、怪物语音、逐句配音。
2. **作为裸容器，躺在归档之间的空隙里**：disc 1 `ud1.bin` 两段（143 654 912 字节 @ `0x28EBD800`，146 067 456 @ `0x3FC44000`），disc 1 `ud2.bin` 21 段共 135 483 392 字节。它们是一串首尾相接的 `AAC ` 容器，**100.00% 的长度都有归属**。只扫 `SOND` 永远找不到音乐。

由于容器自报总长度，一串容器不需要外部索引；而它们位于空隙中，也没有归档指向它们。

## 3. 容器结构

大端，0x30 字节头 + 目录 + 声音 + 播放表。

| 偏移 | 大小 | 字段 |
| --- | --- | --- |
| `0x00` | 4 | `AAC ` |
| `0x04` | 4 | 容器总大小（含头） |
| `0x10` | 4 | 目录项数 |
| `0x14` | 4 | 目录偏移（`0x30`） |
| `0x18` | 4 | 目录区大小 |
| `0x1C` | 4 | 播放表偏移 |
| `0x20` | 4 | `0x00010003`，版本，恒定 |

块结构沿用 ASF 的 16 字节块头：

```
AAC                    容器
  DIR                  计数 + 每声音一项
    dirn               一项，0xA0 字节
  WAVE                 一个声音
    strm               流描述
  PLBK                 每个目录项一条播放记录
```

`PLBK` 是例外：它后面的两个词不是"保留零 + 步长"，有的容器里会直接走出文件，所以读取器按声明大小前进（全部 20 755 条记录都是 `0x70`）。

## 4. 目录与"原始文件名"

`dirn` 里 `+0x10` 是 0x80 字节的 NUL 填充名字，`+0x90` 是 `WAVE` 偏移，`+0x9C` 是条目 id（高 16 位）。

名字是**构建声音时的原始 `.wav` 文件名**：

```
BGM_24_BATTLE_SCENE.wav
DOOR_001_WOOD_S_OPEN.wav
AYA_SP_0001.wav
```

于是游戏自带一份完整、可读的音频清单——这是这个格式最有用的地方。偏移为零的条目是空槽：22 593 个条目里有 350 个。

## 5. 校验与数量

以 disc 1 `ud1.bin` 计：

* 830 个非空 `SOND`，共 **22 243 个声音**，全部通过 `tools/aac.py` 的每一项检查；
* **79 首音乐**，全部通过标准 XMA2 解码器解码；
* 输出侧支持两种：包成 RIFF 的 XMA2，或直接解成 PCM；
* 循环点、采样率、时长都在容器里。

播放表 `PLBK` 的形状已知（23 个值），但从没对照引擎行为验证过。

## 6. 遗留问题

* `WAVE +0x08` 处一个八字节字段，在 2 404 个声音里恒为 `0x995A7C80_00000015`，其余为零。
* `+0x24` 的采样计数到底数什么。
* `PLBK` 的 23 个值与引擎用法的对应。
* 音乐编号 35、45、46、55、74 在两张盘上都不存在——被删了，还是藏在未走到的区域。
* 波表合成器（`WavetableSynth`）的用法未追进数据。

## 7. 相关工具

